# 家電・家具の説明書管理アプリ 計画メモ

## 1. アプリの目的

家電・家具・住宅設備などの説明書がどこにあるのかわからなくなる問題を解決するための個人向けアプリを作る。
主な目的は以下。

- 家電・家具・設備ごとに説明書PDFを管理する
- 製品名、メーカー、型番、設置場所などから探しやすくする
- PDFをアプリ上で閲覧できるようにする
- メンテナンス周期を登録して、適切なタイミングで確認できるようにする
- 将来的にはAIで説明書PDFを解析し、メンテナンス候補や消耗品情報を抽出する
- 将来的には説明書に対してAI検索・AI Q&Aできるようにする
  最初は個人利用を前提にするが、将来的に他ユーザーへ展開できる可能性も残す。

7. 認証方針

本番は Cloudflare Access で Worker 全体を保護し、家族のメールアドレスだけを許可する（2026-09-26 決定、ADR 0005）。
アプリは Access が付与する JWT（Cf-Access-Jwt-Assertion ヘッダー）を検証し、検証できたら家族共有の user_id を返す。
ログイン画面・セッション・ユーザーテーブルはアプリ側に持たない。
家族以外にも公開する段階で Better Auth + Google OAuth を検討する。

最初のローカルMVPでは認証なしで始める。

その代わり、最初から全データに user_id を入れる。

ローカルでは固定値を使う。

export async function requireUserId() {
  return "local-user-1"
}

本番では Access の JWT を検証する実装に差し替える。

export async function requireUserId() {
  const jwt = request.headers.get("Cf-Access-Jwt-Assertion")
  if (!jwt || !(await verifyAccessJwt(jwt))) throw new Error("Unauthorized")
  return env.APP_USER_ID // 家族共有の ID
}

重要なのは、アプリ全体に "local-user-1" を直接書かず、必ず requireUserId() のような関数経由にすること。

22. Secrets 管理方針

以下はsecretとして扱う。

OPENAI_API_KEY
CLOUDFLARE_API_TOKEN（GitHub Actions でデプロイする場合のみ）

D1 / R2 は Worker バインディングで接続するため、接続トークンやアクセスキーは不要。

（Better Auth を導入する場合は BETTER_AUTH_SECRET と GOOGLE_CLIENT_SECRET が追加で必要）

Terraform state にsecretが残る可能性があるため、重要なsecretをTerraformで管理しすぎない。

29. この計画の狙い

1. 家電・家具を登録できる
2. PDFを保存・閲覧できる
3. メンテナンスタスクを登録できる
4. 期限が近いものを確認できる
5. AIでメンテナンス候補を抽出できる
6. AI候補を承認してタスク化できる
7. ローカル実装から本番構成へ移行しやすい
