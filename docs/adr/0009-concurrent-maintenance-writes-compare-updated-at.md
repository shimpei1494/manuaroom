# 完了・スキップ・取り消しの同時操作は、タスクの更新日時を比べて守り、記録とタスクは 1 つの batch で書く

完了・スキップ・取り消しは、タスクを読み、次回予定日を計算し、記録とタスクを書く。これを別々の D1 の呼び出しで行っていたため、連打や家族の同時操作で 2 つの操作が重なると、片方の更新が失われたり、記録の戻し先 (`maintenance_logs` の `previous_*`) が食い違ったりした。完了を 2 回同時に押すと、2 回目の記録の戻し先が「最初の状態」になり、「元に戻す」を 1 回押しただけで 2 回分が消えた (ADR 0006 の取り消しの約束が破れる)。

## 決めたこと

- 3 つのユースケースは、書くときに「タスクの `updated_at` が、読んだときのままか」を条件にする。変わっていたら何も書かず、読み直すところからやり直す (最大 5 回。それでも重なれば `もう一度お試しください` と返す)。やり直しは、書けなかった = 別の操作が書けたということなので、数回で順番が回ってくる。
- 記録の追加・削除とタスクの更新は、D1 の `batch` (1 トランザクション) で 1 つにまとめる。`MaintenanceLedgerPort` (`appendLog` / `revertLog`) がその単位で、タスクの更新が 1 行に効いたとき (`changes() > 0`) だけ、記録を書く・消す。効かなかったときは記録にも触らない。
- 取り消しは、タスクを先に読み、そのあとに記録の一覧を読む。記録のほうが新しいぶんには、書き込み時の比較が見つける。逆の順で読むと、他の操作の結果を古い記録で巻き戻してしまう。
- やり直しのたびに、時計を読み直す。記録の作成時刻が、書き込みの順と食い違わないようにするため (取り消せるのは `createdAt` が最新の記録、ADR 0006)。
- スキーマは変えない。`updated_at` は、完了・スキップ・取り消し・編集のどれでも書き換わる。

## 守れていること・いないこと

- 守れる: 完了・スキップ・取り消しの 2〜3 個の重なり。`.claude/skills/verify-maintenance-log-races` が、全ての実行順序で「時刻順に 1 つずつ行った結果のどれかと一致する」「取り消しを押し続けると最初の状態に戻る」を確かめる。
- 守れない: `updated_at` はミリ秒単位。同じミリ秒に 3 つ以上の操作が重なり、さらに特定の順に並ぶと、比較をすり抜けうる。現実の操作ではほぼ起きないとみて、バージョン列は足さなかった。
- 守れない: タスクの編集 (`update-maintenance-task`) は読んでから全項目を書くので、完了などと重なると、完了の結果を上書きしうる。編集は `updated_at` を書き換えるので、重なった完了・スキップ・取り消しのほうは検出してやり直せる。編集側は別に直す。

## 不採用案

- **記録とタスクを `batch` にまとめるだけ**: 2 つの書き込みは切り離せるが、読んだ内容が古いままなので、戻し先の食い違いは残る。
- **バージョン列 (`version`) を足す**: ミリ秒の衝突まで守れるが、マイグレーションと全ての書き込み経路の変更が要る。現状の重なり方に対しては過剰とみた。
- **重なったらエラーにして、利用者にやり直させる**: 連打した 2 回目が失敗して見える。直列に行った結果と同じ (2 回とも記録される) ほうが、利用者の意図に合う。
- **Durable Objects などで操作を直列化する**: Cloudflare だけで完結する構成 (ADR 0005) に、状態を持つ部品が増える。1 世帯の台帳には重い。
