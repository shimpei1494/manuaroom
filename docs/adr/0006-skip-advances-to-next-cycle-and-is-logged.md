# スキップは「スキップした日 + 周期」で次回予定日を立て直し、実施記録とは別の種類のログとして残す

Maintenance Task に「スキップ」操作を追加する。スキップすると、その回は実施せずに次回予定日 (`next_due_date`) を「スキップした日 + interval」で再計算する。`last_done_at`（最終実施日）は変えない。スキップした事実は `maintenance_logs` に `kind = 'skipped'` の行として残し、実施（`kind = 'done'`）と区別する。

理由：フィルター交換などは多少遅れても困らないことが多く、期限超過のまま残すか、やっていないのに「完了」を押すかの二択だと台帳が信用できなくなる。スキップをログとして残せば「最後に実際にやったのはいつか」と「何回続けて先送りしているか」が両方わかる。再計算の起点をスキップした日にするのは ADR 0001（完了日基準）と揃えるためで、長く放置したタスクをスキップしても、すぐにまた期限超過にならない。

## 例

「フィルター交換 / 6か月ごと」、最終実施 1/10、次回予定 7/10 のタスクを 7/20 にスキップした場合：

- `next_due_date` = 1/20（7/20 + 6か月）
- `last_done_at` = 1/10 のまま
- 画面表示: 「1回スキップ中 ・ 最終実施 1/10（〇日前）」

さらに 1/25 にもスキップすると「2回スキップ中」。次に完了した時点でスキップ回数は 0 に戻る。

## 決めたこと

- スキップ回数は保存せず、`last_done_at` より後の `skipped` ログの件数として数える（ログが唯一の事実、ADR 0001 と同じく task 側の値はキャッシュ扱い）。
- interval が未設定のタスクはスキップできない（次の周期がないため）。予定日を変えたいときは編集で直す。
- スキップの取り消しは、直前のスキップログを削除して `next_due_date` を戻す形で後から追加できる。MVP では確認ダイアログのみ。

## 不採用案

- **予定日基準（元の `next_due_date` + interval）**: 周期のリズムは保てるが、大きく遅れたタスクはスキップしても期限超過のまま残る。
- **スヌーズ（任意の日付まで延期）だけを用意する**: 「次の周期まで」という一番多い使い方に毎回日付選択が必要になる。任意日付への延期は必要になったら別操作として足す。
- **task に `skip_count` カラムを持つ**: 表示は楽だが、ログと食い違う余地が生まれる。件数が少ないのでログから数えれば十分。
